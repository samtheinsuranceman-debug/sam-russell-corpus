### A note on the base, recorded for the record

`sam-russell-corpus` **has no root `package.json`.** It is a corpus: ~990 MB of it is
books, correspondence, audio and research. The buildable application inside it is
`russell-capital-systems/`, and every build, typecheck and test result in document 3 of this
PR was produced from that directory.

Separately, the repository that currently answers on russellcapitalsystems.com is
`russell-capital`, not this one. That is a deployment fact, not an argument against this
decision — and §1.4 shows the decision is well supported on the merits. It is recorded here
only so that no future reader assumes "canonical base" and "currently deployed" are the same
repository. **No DNS, hosting, or deployment change is proposed by this PR.**

## 1.4 Why the base holds up on the merits

Measured, `russell-capital-systems` is the stronger engineering artifact everywhere it counts:

| Layer | Canonical base | `russell-capital` (live) | Verdict |
|---|---:|---:|---|
| Shared modules | **187** | 63 | Base, decisively — live has only 4 the base lacks |
| Server modules (non-test) | **147** | 49 | Base, decisively — live has only 3 the base lacks |
| DB tables | **155** | 116 | Base — live has only 7 the base lacks |
| Test files | **226** | 98 | Base |
| Tests passing | **4,138 / 0 failing** | 2,086 / **95 failing** | Base, decisively |
| Route manifest emitted at build | **yes** (`routes.json`) | no | Base |
| Page files | 325 | 687 | **Live** — this is the migration surface |

The base is the better *foundation*; the live build holds the larger *page catalogue*. That is
exactly the shape that makes "base + phased page migration" the right strategy, and it is why
the 391-page figure in document 4 is a migration plan rather than a merge.
